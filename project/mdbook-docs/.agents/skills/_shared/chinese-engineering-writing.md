# 中文工程文档写作规范

本规范是共享写作规则。目标是让开发者在 30 秒内看清结论、状态、证据和风险，而不是生成完整报告或复述 Agent 的推理过程。

## 信息顺序

开发文档优先按以下顺序组织：

1. 一句话结论；
2. 当前状态或最终结果；
3. 关键流程、关键变更或关键决策；
4. 代码证据；
5. 风险、限制和待验证事项；
6. 必要的详细解释；
7. 折叠的原始请求。

让文档前 30 至 50 行足以说明主要情况。正文开头可以写一行简短的“任务来源”，但不得逐字重复完整请求。

## 受控中文

- 使用简体中文。代码标识符、命令、路径和项目既有术语保持原样。
- 一个句子只表达一个主要事实、动作、条件或判断。
- 明确写出主体、动作和对象。
- 同一概念只使用一个统一名称，不为了语言变化而替换技术术语。
- 先写结论，再写原因和证据。
- 优先使用短段落、列表、表格和流程图。
- 单个普通段落原则上不超过 4 句。
- 比较多个方案时优先使用表格。
- 操作流程使用编号步骤。
- 数据流或调用关系复杂时考虑使用 Mermaid 图；具体条件遵循“可视化和 Mermaid”一节。
- 不使用“显然”“非常重要”“大幅提升”“较好”等没有证据的评价。
- 不写与当前问题无直接关系的通用技术科普。
- 不重复其他文档已经记录的背景，改为链接相关文档。
- 不逐行解释容易直接读懂的代码。
- 不推测代码、配置、测试或用户输入中没有提供的事实。
- 不确定的信息标记为“待确认”。
- 尚未验证的信息标记为“待验证”。
- 尚未实现的内容标记为“未实现”。
- 明确区分计划、当前现状、已实现事实和已验证结果。
- 数值必须带单位。
- 缩写首次出现时说明全称；项目中已经统一定义的常用缩写除外。
- 没有实质内容的可选章节直接省略，不生成“无”“暂无”或 TODO 占位文字。
- 默认不写重复全文的“总结”章节。

## 可视化和 Mermaid

Mermaid 是可选表达方式，不是文档的默认组成部分。按以下顺序处理：

1. 先判断图是否能明显降低理解成本。只有复杂调用链、数据流、状态变化、多分支流程或组件关系难以用短列表表达时，才使用 Mermaid。
2. 简单顺序、少量映射或两三个对象之间的关系使用编号步骤、列表或表格。此时不要检查 Mermaid 环境，也不要生成 Mermaid 代码。
3. 确定需要 Mermaid 后，运行 `command -v mdbook-mermaid` 检查当前环境。
4. 若命令不存在，不要安装依赖，不要生成无法渲染的 Mermaid；改用列表、表格或纯文本流程，并在必要时标记可视化未启用。
5. 若命令存在，检查 `<mdbook-root>/book.toml` 是否已有 `[preprocessor.mermaid]`。只有当前文档确实需要 Mermaid 且尚未配置时，才运行 `mdbook-mermaid install <mdbook-root>`。不要在 mdBook 初始化阶段预先启用。
6. 使用 Mermaid 后运行 `mdbook build <mdbook-root>`。构建失败时修正图或降级为普通 Markdown，不保留已知无法构建的内容。

### 图形可读性约束

- 默认使用 `flowchart TB` 或 `flowchart TD`，让节点纵向排列。
- 只在线性流程节点少且标签短时使用 `LR`。横向图在正文宽度内必须保持文字清晰。
- 一张图只回答一个问题。不要在同一张图中同时展开调用链、状态机、异常处理和所有实现细节。
- 一张图原则上不超过 8 个核心节点。超过时优先拆成总览图和局部图；辅助节点不用于绕过此限制。
- 节点和边使用短标签。完整条件、参数、代码证据和例外规则放在图前后的列表或表格中。
- 对称或重复管线优先画一条通用管线，再用列表说明实例差异。只有差异本身需要可视化时才分别绘制。
- 出现多组子图、交叉连线或长标签时，优先拆图。不要通过缩小文字把所有内容塞进一张图。
- `mdbook build` 成功后仍要检查生成页面在正常缩放下是否可读。文字过小或连线难以追踪时，改为纵向、拆图或降级为普通 Markdown。

Mermaid 图只表达正文已经确认的事实。不要为了视觉效果增加未提供的节点、流程或关系。

## 代码证据

涉及代码实现的结论应尽可能附带：

- 文件路径；
- 类、函数、结构体、配置项或命令名称；
- 必要时的行号；
- 修改前后的行为差异；
- 实际执行过的验证命令；
- 验证结果。

不要粘贴大段代码。单个代码片段默认不超过 20 行。除非代码片段本身就是解释对象，否则优先引用文件路径和符号名称。

## 原始请求

不要把完整原始请求展开放在主标题后。将触发当前 skill 的完整用户消息逐字放在文档末尾，不包含 system、developer 或隐藏上下文消息。使用以下格式：

```html
<details>
<summary>原始请求</summary>

这里逐字保留触发 skill 的用户消息。

</details>
```

原始请求只用于追溯，不得影响正文首屏阅读。

## 长度控制

- 一句话结论不超过 2 句。
- 当前状态不超过 5 项。
- 单个普通段落不超过 4 句。
- 单个问题或风险说明优先控制在 120 个汉字以内。
- 背景说明原则上不超过全文的 20%。
- 能通过文件链接表达的信息不重复展开。
- 只有用户明确要求“详细解释”“教程”或“深入分析”时，才展开长篇原理说明。
