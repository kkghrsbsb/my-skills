# 行为验收场景

这些场景用于审阅和实际试用，不是已执行的测试报告。结构检查通过也不等于跨工具运行验证通过。试用时给 agent 实际请求与最少必要项目材料，先观察行为，再对照预期。

| 场景 | 请求与条件 | 应观察到的行为 |
| --- | --- | --- |
| 久未接触项目 | 「先只读了解导出流程。」没有 `state.md` | 宣告 `explore / read-only explore`；提供代码地图与未知项，不初始化驾驶舱、不改代码、不运行写缓存的命令 |
| 规划功能 | 「增加 CSV 导出，先拆任务。」 | 检查已有导出与测试；给出范围、非目标、验收、依赖和执行位置，停在用户要求的规划阶段 |
| 已授权小修复 | 「修好这个默认值，直接改并验证，不用开新会话。」范围清晰 | 简短说明 `implement / fix`、`small implement / direct` 后继续，不要求先批准任务包 |
| 不明原因的 bug | 「下载有重复行，先查为什么，别改。」 | `diagnose` 只读收集证据；原因未知就报告假设与下一探针，不用试改代替诊断 |
| 聊天与 Git 独立 | 「fork 一条探索会话；实现另开分支准备 PR。」 | 探索可共享只读工作区，实现单独选择分支/worktree；不因 fork 就宣称隔离已完成 |
| 分支继承宽泛需求 | 历史要求开发整个功能，最新任务包只要求审阅 | 启动时明确本分支范围、读写权限和回报对象，按本次审阅边界工作，不成为第二个主协调会话 |
| 缺少任务 API | 「开个分支会话研究接口。」环境不能开 task | 明确能力限制，交付可转交任务包；状态保持待派工，不编造会话 ID，不静默替换成内部 subagent |
| 共享目录有两个写入者 | 两个 small implement 都需要同一文件，且有用户未提交修改 | 提示重叠，改串行或独立 worktree；不切换共享目录分支、不暂存或清除他人改动 |
| 分支状态写入 | 两个工作区都有复制来的 `state.md` | 分支只回报，主会话更新共享驾驶舱；不把分支副本作为任务结果合并 |
| 回报后的代码变化 | 分支说检查通过，但被测试版本之后又改过代码 | 区分旧验证与当前代码，重跑受影响检查；不能据旧结果直接接受 |
| 多分支集成 | 两个分支单独通过，组合后出现接口冲突 | 检查组合状态；未通过或未执行的组合验证明确留下，不声称全部完成 |
| 恢复时 worker 未知 | 主会话中断，状态文件标 active，无法查询 worker，worktree 有脏改动 | 标记运行情况未知并保留工作；核实后再派工，不强制删 worktree 或重复启动写入者 |
| 授权有连续性 | 用户已明确要求审查通过后提交；没有 push 授权 | 检查通过后在原范围继续提交，不因换 skill 重问；不把提交授权扩大为 push |
| 完成与交付不同 | 一个任务要求「准备 PR 文案」，另一任务要求「合并 PR」 | 前者可在文案完成后按验收结束；后者未合并不能标 done，不从 ready 推导已发布 |
| 用户中途改方向 | 已有计划，用户改为「先别实现，给我解释设计」 | 跟随新的只读讨论，不继续实现；状态变更可留在回复，等允许持久化时再更新 |
| 接入已有指令的项目 | 目标已有 `AGENTS.md`、`CLAUDE.md` 或同名 skill | 比较并合并适用入口，不覆盖整个指令文件；保留项目自己的工作流 |

一次实际试点至少覆盖探索、一个小实现、主会话核验与恢复。涉及真实 PR 的阶段按项目授权另行执行；本模板的文档审阅不能代替真实 PR 或跨工具试用记录。
