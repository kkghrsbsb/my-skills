# agent-dev-flow

让一个主会话持续维护项目认知、任务队列和下一步，再按需要把明确任务交给分支会话。适合新接手项目、隔一段时间回来开发，以及从前期计划进入中期维护的工程项目。

这套模板使用普通 Markdown，包含 5 个英文 skill、共享协议和中文交接模板。对话与运行时记录默认跟随用户语言。不依赖 mdBook、mycommit、运行脚本、hooks 或指定模型。

## 接入项目

将本模板的 `.agents/skills/agent-*` 五个目录与 `.agents/dev-flow/` 一起加入目标项目，保持相对位置。共享协议和模板是技能的一部分，单独复制一个 `SKILL.md` 会丢失引用。

先比较目标文件：已有同名 skill 或协议时审阅差异再合并；已有 `AGENTS.md` 或 `CLAUDE.md` 时，只合并适用的入口段落。不存在时才添加本模板对应入口。不要直接用递归复制覆盖整个 `.agents` 或项目指令文件。这里提供的 README 是模板说明，不能替换目标项目的 README。

支持技能发现的工具可以按自己的方式加载这些技能；也可以直接要求 agent 阅读对应的 `SKILL.md`。不同工具的发现路径和调用语法需要按实际环境适配，协议本身通过文件路径即可读取。模板不承诺所有工具自动发现 `.agents/skills`，也不自动创建聊天分支。

首次需要保存项目状态时，由主会话参考 [state.example.md](.agents/dev-flow/state.example.md)，根据实际仓库生成 `.agents/dev-flow/state.md`。示例内容不代表你的项目状态。只读了解项目时，在聊天中回报即可。

团队共享的目标、任务和证据可以纳入版本管理；个人聊天链接、机器上的 worktree 路径可留在本地记录。接入时按项目习惯决定 `state.md` 是否跟踪，不自动修改 `.gitignore`。分享模板前保持示例通用，不写入真实私有项目内容。

## 主会话启动方式

主会话开始维护一个项目时，先用一句话判断自己的启动方式。这只是提醒，不是硬流程。

| bootstrap mode | 适合场景 | 建议第一步 |
| --- | --- | --- |
| `fresh` | 新项目或刚开始引入这套工作流 | 确认目标，决定是否创建驾驶舱 |
| `reconstructed` | 项目已经开发过，但旧会话不可用或不再可信 | 先 `read-only explore`，从仓库事实重建认知 |
| `resumed` | 同一条主线中断、压缩上下文或短暂停顿后继续 | 对照驾驶舱、当前 diff 和任务状态恢复 |
| `transferred` | 团队成员、多设备、不同工具或新主会话接手 | 检查共享状态、Git 现状、归属和未知活跃任务 |

已有项目第一次接入时，可以这样开场：

> 这个项目之前开发过一段时间，但旧会话已废弃。现在导入 `agent-dev-flow`。请以 `reconstructed` 启动，只读理解仓库、近期改动和风险，先不要写文件。完成后再问我要不要创建 `.agents/dev-flow/state.md`。

团队或多设备接手时，可以这样开场：

> 这是一个使用 `agent-dev-flow` 的项目。我在新的主会话继续维护。请以 `transferred` 启动，只读检查 `.agents/dev-flow/state.md`、Git 状态、近期提交和未知活跃任务，再建议我继续哪个任务或先同步哪些信息。

`state.md` 不是权威数据库。权威仍然是当前仓库、Git 历史、真实 diff、真实任务状态和你的确认。旧会话、旧驾驶舱和历史任务包都只能作为线索。

## 五个入口

| Skill | 适合什么时候用 | 结果 |
| --- | --- | --- |
| [agent-orient](.agents/skills/agent-orient/SKILL.md) | 不熟悉项目、想重新建立认知 | 主流程与模块地图、代码证据、未知项 |
| [agent-plan](.agents/skills/agent-plan/SKILL.md) | 需求还需要拆解，或 bug 原因未明 | 有边界的任务、方案、验收与工作区建议 |
| [agent-branch](.agents/skills/agent-branch/SKILL.md) | 需要分出会话处理明确任务 | 任务包、会话与工作区定位、回报约定 |
| [agent-gate](.agents/skills/agent-gate/SKILL.md) | 收到探索报告或实现结果 | 基于实际证据的判断与下一步 |
| [agent-resume](.agents/skills/agent-resume/SKILL.md) | 中断、换会话或回到已有任务 | 对照现状恢复任务，避免重复派工 |

不用依次调用五个入口。清楚的小改动可以在主会话直接做；不了解的问题先探索；找不到原因的 bug 先诊断。`diagnose` 暂由 `agent-plan` 与任务包承接，后续有真实使用需求再拆独立 skill。

## 交互中的显式提醒

agent 在开始实质工作或调整策略时，用一两句话说明自己的选择，例如：

> 这次是 `explore`，采用 `read-only explore`，开一个继承上下文的分支会话。先弄清导出数据流和测试入口，结果回来后再决定实现范围。

> 这是 `implement / fix`，改动集中在一个模块，采用 `small implement`，留在主会话完成。验证已有授权，不再单独确认。

提醒后按已有授权继续；只有真正影响范围、结果或授权的缺口才需要提问。你可以随时改变任务类型、工作区和会话策略，下一次有意义的状态更新记录这个选择即可。

| 工作区档位 | 使用方式 |
| --- | --- |
| `read-only explore` | 当前工作区只读；也适用于诊断、计划与审查，不写驾驶舱，不运行会产生文件的测试 |
| `small implement` | 当前工作区小改动；检查已有修改与文件归属，共享目录不切换 Git 分支 |
| `pr implement` | 独立 Git 分支与 worktree；适合较大功能、并行开发与计划提 PR 的任务，记录实际基线 |

会话另行选择：大量上下文用 `fork`，清楚的任务包用 `create`，短讨论用 `direct`。聊天分支不会天然隔离文件，也不等于 Git 分支。多个写入任务有重叠时，串行或改用独立 worktree；文件不重叠但接口有依赖时，仍需安排集成验证。

## 驾驶舱和交接

主会话维护目标、认知摘要、任务队列、分支定位、重要决定和下一步。分支只负责自己的任务并回报，避免多个会话同时改写 `state.md`。主会话在任务派出、报告返回、方向变化或暂停等节点更新，不逐轮记聊天流水。

较大任务可使用 [任务包](.agents/dev-flow/templates/task.md) 和 [回报模板](.agents/dev-flow/templates/report.md)；小任务直接在聊天里交接。必需信息是目标、范围、验收、必要上下文、执行位置与回报要求，其他字段按需裁剪。

`explore / plan / diagnose / implement / review / gate` 表示当前活动；`feature / fix / docs / refactor / test / chore` 表示改动性质，两者独立。Git 分支名沿用目标项目及工具的约定，模板不强制提交格式。

任务可用 `queued / active / blocked / ready / done / dropped` 表达状态。分支完成回报后先是 `ready`，主会话评估后再决定下一步。`done` 对应本任务的验收要求；本地完成、已提交、已开 PR、已合并需另记，不能相互替代。

## 一次使用示例

1. 「这个项目我很久没碰了，先只读弄清导出流程。」主会话选择探索，直接进行或按已授权的方式开探索会话。
2. 探索返回入口、数据流、测试位置与未知项。你提出「增加 CSV 导出」，主会话拆成范围清楚的 `implement / feature` 任务。
3. 主会话提示采用 `pr implement`，检查起点与未提交上下文，准备任务包并按授权派工。
4. 分支回报实际改动、验证命令与结果、测试对应的代码状态，以及未解决事项。
5. 主会话审阅 diff，决定继续修改、集成、提 PR 或放弃。合并多个分支后检查组合结果，不能只引用各自通过的测试。
6. 之后换会话，用 `agent-resume` 对照驾驶舱和实际仓库恢复任务；工具无法查询的分支标为状态未知，先核实再重新派工。

这里的流程是技能使用示例。本模板的开发过程本身无需依赖这些新技能才能进行。

## 跨工具边界

核心协议只依赖可读文件和会话交接。有任务 API 时按实际能力创建、分叉和接收回报；没有时提供任务包，由用户在另一个会话打开，或按请求留在主会话执行。不凭空报告会话已创建，也不把内部 subagent 静默当作用户可见的聊天分支。

恢复上下文时以当前代码、diff 和可观察的任务状态为准。旧状态不能代替当前证据；主会话中断也不表示分支已经停止。保留未完成工作，不用删除脏 worktree 的方式恢复。

commit、push、开 PR、合并、安装依赖和清理工作区按用户实际授权执行。模板不默认开启这些动作，也不要求对已经授权的同一动作重复确认。
